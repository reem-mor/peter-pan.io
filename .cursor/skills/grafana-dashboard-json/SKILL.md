# Grafana Dashboard JSON — Generation Rules

## Golden rules
1. **Never invent schema fields.** Use only the fields shown in the template below.
   If a panel type or option isn't listed here, ask before using it.
2. **Fixture-first.** Every demo scenario (payments-latency, disk-pressure,
   error-spike) has a committed fixture JSON under `fixtures/dashboards/`.
   The LLM path must produce JSON that passes the same validator as fixtures.
3. **Validate before POST.** Run the JSON through the service's validator
   (required keys, panel gridPos non-overlap, datasource uid present) before
   any API call. A 200 from Grafana is not the validation — Grafana silently
   accepts some malformed panels and renders them empty.

## Minimal valid dashboard (the template — extend, don't replace)
```json
{
  "dashboard": {
    "id": null,
    "uid": null,
    "title": "INCIDENT <id> — <short description>",
    "tags": ["peter-pan", "generated", "<incident_class>"],
    "timezone": "browser",
    "schemaVersion": 39,
    "refresh": "30s",
    "time": { "from": "now-1h", "to": "now" },
    "panels": []
  },
  "folderUid": "peter-pan",
  "overwrite": false,
  "message": "Generated by PETER PAN Dashboard Generator"
}
```

## Panel template (timeseries — the default panel type)
```json
{
  "id": 1,
  "type": "timeseries",
  "title": "<metric name>",
  "gridPos": { "h": 8, "w": 12, "x": 0, "y": 0 },
  "datasource": { "type": "prometheus", "uid": "$DS_UID" },
  "targets": [
    { "refId": "A", "expr": "<promql>", "legendFormat": "{{instance}}" }
  ],
  "fieldConfig": { "defaults": { "unit": "short" }, "overrides": [] }
}
```

Allowed panel types for this project: `timeseries`, `stat`, `gauge`, `table`.
Nothing else without asking.

## Layout rules
- Grid is 24 units wide. Standard layout: 2 panels per row, `w: 12, h: 8`.
- `gridPos.y` increments by 8 per row. Panels must not overlap.
- Max 6 panels per generated dashboard — relevance over completeness.
  The whole point is a FOCUSED dashboard, not another 40-panel wall.
- Panel `id` values must be unique integers starting at 1.

## Panel selection by incident_class (guidance for the LLM prompt)
| incident_class family | Default panels |
|---|---|
| latency / performance | p95 latency (timeseries), request rate (timeseries), error rate (stat) |
| errors / availability | error rate by code (timeseries), success ratio (gauge), top failing endpoints (table) |
| resource / capacity | CPU/mem (timeseries), disk usage (gauge), saturation trend (timeseries) |

## Grafana HTTP API
- Create/update: `POST /api/dashboards/db` with the full body above.
- Auth: `Authorization: Bearer $GRAFANA_API_TOKEN` — token comes from env
  (see .env template). NEVER hardcode, never log the token.
- Success response contains `"url"` — return that to the caller; the service
  response schema is `{dashboard_url: str, uid: str, panels_count: int}`.
- Local dev Grafana: `http://localhost:3000` (docker, grafana-oss).
- Datasource uid: resolve once at service startup via `GET /api/datasources`,
  cache it; do not hardcode uids in generated JSON (fixtures may use the
  placeholder `$DS_UID`, replaced at POST time).

## What NOT to do
- No alerting rules, no annotations, no template variables (`templating`) in
  generated dashboards — out of scope for the demo.
- No `overwrite: true` unless updating a dashboard the service itself created
  (match by uid prefix `pp-`).
- Do not generate PromQL against metrics that don't exist in the demo
  Prometheus; the valid metric names list lives in
  `fixtures/dashboards/metrics_catalog.json` — select only from it.
